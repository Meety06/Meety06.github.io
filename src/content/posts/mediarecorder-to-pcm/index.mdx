안녕하세요. Meety 서비스의 FE 개발자 chloe입니다.

앞선 글에서는 WebSocket의 <code>send()</code> 성공만으로 서버 수신을 보장할 수 없어, 청크를 IndexedDB에 남기고 ACK를 기준으로 재전송하도록 바꾼 이유를 정리했습니다. 그런데 청크를 다시 보낼 수 있게 된 뒤에도 질문이 하나 남았습니다. **재연결된 AI가 그 청크를 읽을 수 있을까요?**

결론부터 말하면, 당시 사용하던 WebM/Opus 스트림에서는 어려웠습니다. 이 글에서는 MediaRecorder를 AudioWorklet 기반 PCM 캡처로 바꾼 이유와, 그 선택이 회의 종료 시 파일 준비 시간을 어떻게 바꿨는지 설명하겠습니다.

## 재전송할 수 있는 바이트와 디코딩할 수 있는 바이트는 달랐습니다

기존 흐름에서 MediaRecorder는 약 20ms마다 WebM/Opus 청크를 만들었습니다. FE는 같은 청크를 IndexedDB에 저장하고 WebSocket으로 보냈습니다. 회의 종료 시에는 저장한 청크를 합치고 ffmpeg.wasm으로 MP4를 만든 뒤 업로드했습니다.

문제는 BE와 AI 사이의 연결이 끊겨 AI 디코더가 새로 시작되는 경우였습니다. 저희가 사용한 WebM 스트림의 초기화 정보는 첫 부분에 있었습니다. 새 디코더에 중간 청크부터 전달하면, 바이트가 빠짐없이 도착해도 앞선 초기화 정보를 알지 못해 해석할 수 없었습니다. ACK와 재전송은 **전달 누락**을 다루지만, 이것은 **오디오 스트림을 중간부터 해석하는 문제**였습니다.

선택지는 세 가지였습니다. MediaRecorder의 압축 결과를 다시 PCM으로 풀거나, MediaRecorder와 AudioWorklet을 병행하거나, 처음부터 AudioWorklet에서 PCM을 만드는 방식입니다. 앞의 두 방식은 전사에 쓰는 PCM 구간과 녹음 파일에 쓰는 압축 청크의 경계를 다시 맞춰야 했습니다. 저희는 **전송·재전송·파일 생성의 출발점을 하나의 PCM으로 맞추는 방식**을 골랐습니다.

## 100ms의 PCM 조각을 직접 만들었습니다

새 흐름에서는 마이크 입력을 16kHz <code>AudioContext</code>에 연결하고, AudioWorklet에서 채널을 모노로 합친 뒤 Int16 little-endian 바이트로 바꿉니다. Worklet은 128프레임씩 입력을 받으므로, 1,600샘플이 모일 때마다 **100ms, 3,200바이트**의 PCM 청크 하나를 내보냅니다. 일시정지나 종료 때는 100ms에 못 미치는 마지막 조각도 <code>flush</code>로 내보냅니다.

메인 스레드는 이 청크에 세션 전체에서 이어지는 <code>seq</code>와 누적 샘플 위치인 <code>startSample</code>을 붙입니다. 이어서 IndexedDB에 저장하고, 8바이트 순번 헤더와 PCM을 WebSocket으로 보냅니다. 서버가 보낸 ACK는 저장된 청크의 상태를 바꿉니다. 압축 컨테이너의 앞부분이 필요한 WebM과 달리, 이 PCM 조각은 샘플레이트·채널·비트 깊이라는 형식을 알고 있으면 해당 구간부터 처리할 수 있습니다.

## PCM만으로는 녹음 파일 문제가 끝나지 않았습니다

PCM은 중간 구간부터 처리하기 쉽지만 압축되지 않아 큽니다. 16kHz·모노·16비트로 계산하면 30분 회의의 원본 PCM은 약 57.6MB입니다. 이 데이터를 종료 시 한꺼번에 변환하면, 전송 문제를 해결하는 대신 종료 대기를 늘릴 수 있었습니다.

그래서 파일용 인코딩 시점도 바꿨습니다. 녹음 중 들어오는 PCM을 48kHz로 업샘플링하고 WebCodecs <code>AudioEncoder</code>에 넣어 AAC 프레임을 점진적으로 만들었습니다. 프레임과 디코더 설정은 IndexedDB에 저장합니다. 종료 시에는 남은 프레임을 마무리하고 저장된 AAC 프레임을 MP4로 **묶기만** 합니다. 기존의 종료 시 ffmpeg.wasm 변환과 core 다운로드가 필요 없어졌습니다.

이는 “PCM이어서 빨라졌다”보다 **캡처 방식을 바꾸면서 인코딩을 녹음 중으로 옮겼기 때문에 빨라졌다**는 설명이 정확합니다.

## 파일 준비 시간은 줄었지만 업로드는 남았습니다

스테이징에서 측정한 종료 시 파일 준비 시간은 4분 녹음에서 **4,699ms → 222ms**, 5분 녹음에서 **6,591ms → 289ms**였습니다. 5분 측정 기준 약 95% 감소입니다. 90분 분량 데이터로 측정한 현재 파일 준비 시간은 로컬에서 약 1.0~1.9초였습니다. AAC 비트레이트도 128kbps에서 48kbps로 바뀌어, 90분 파일은 이전 설정 기준 계산값 약 86MB에 비해 새 방식의 로컬 측정값이 33.9MB였습니다.

다만 **파일 준비 시간과 회의 종료 버튼부터 화면 전환까지의 시간은 같지 않습니다.** Slow 4G를 흉내 낸 로컬 환경에서 90분 파일 업로드는 여전히 6.7분 걸렸습니다. 이전 방식의 약 17분은 같은 실험의 실측이 아니라 속도와 크기로 계산한 값이며, 실제 S3 업로드는 이 측정에 포함되지 않았습니다. 수치와 환경은 [느린 네트워크 측정 기록 #309](https://github.com/100-hours-a-week/KTB4-6th-FE/issues/309#issuecomment-6336414559)에 남겼습니다.

파일을 빠르게 준비할 수 있게 됐지만, 새로고침으로 인코더가 사라졌을 때도 이 파일을 이어 만들 수 있어야 했습니다. 다음 편에서는 PCM 원본과 AAC 프레임을 함께 남긴 이유, 그리고 마지막으로 확정된 프레임부터 인코딩을 복구하는 방법을 다룹니다.
