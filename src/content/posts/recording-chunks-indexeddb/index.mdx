안녕하세요. Meety 서비스의 FE 개발자 Chloe입니다.

<p class="recording-opening-question">회의가 끝난 뒤 녹음 파일에서는 분명 발언이 들리는데, 실시간 전사 기록에서는 그 구간이 비어 있다면 어떨까요?</p>

<p class="recording-opening-context">Meety는 회의 중 음성을 서버로 보내 AI가 실시간으로 전사하고, 동시에 브라우저에는 회의가 끝난 뒤 다시 들을 수 있도록 녹음 데이터를 보관합니다. 그런데 네트워크가 잠시 끊긴 회의에서, 녹음은 온전히 남았지만 전사에는 빈 구간이 생기는 상황을 확인했습니다.</p>

단순히 일부 문장이 빠지는 것으로 끝나지 않았습니다. 브라우저가 보관한 오디오와 AI가 처리한 오디오가 서로 달라지면 둘 사이의 타임스탬프가 어긋나고, 그만큼 AI의 화자 분리 정확도도 떨어질 수 있었습니다. 회의 중에는 전사를 보고, 회의 후에는 녹음을 다시 듣는 Meety의 핵심 사용 흐름이 함께 흔들리는 셈이었습니다.

그래서 먼저 오디오가 녹음 파일과 실시간 전사로 갈라지는 지점을 살펴보고, 로컬에서 인터넷 연결을 끊어 같은 상황을 재현한 뒤 브라우저에 저장된 기록과 서버가 받은 기록을 비교했습니다.

## 녹음 파일과 실시간 전사는 어디서 갈라질까요?

앞서 말한 빈 전사 구간을 이해하려면, 먼저 마이크에서 들어온 음성이 어디로 가는지 봐야 합니다. 당시 `MediaRecorder`는 약 20ms마다 WebM/Opus 청크를 만들었고, 브라우저는 같은 청크를 두 경로에 사용했습니다.

- **녹음 파일:** 청크를 브라우저의 OPFS(Origin Private File System)에 기록해 두었다가, 회의가 끝나면 녹음 파일을 만들었습니다.
- **실시간 전사:** 청크를 WebSocket으로 서버에 보내 AI 전사에 사용했습니다.

같은 청크에서 출발하지만 저장과 전송은 별도로 진행됩니다. OPFS에 청크가 남았다고 해서 서버에도 도착한 것은 아닙니다. 당시에는 브라우저에서 보낸 청크가 서버에 확실히 도착했는지 확인할 방법이 없었습니다.

## 브라우저에 남은 청크는 서버에도 도착했을까요?

두 경로의 결과가 실제로 달라지는지 확인하려고, 로컬에서 녹음 중 인터넷 연결을 끊었습니다. 각 세션에서 OPFS에 저장된 청크와 서버가 받은 청크를 비교하고, `send()` 호출 결과와 소켓 종료 시 상태도 함께 기록했습니다.

아래 그림에서 인터넷 연결 상태를 바꿔 두 경로의 차이를 확인할 수 있습니다.

녹음한 오디오가 서버까지 온전히 전달되고 있는지 확인하기 위해, 약 20ms마다 생성되는 오디오 청크를 브라우저에 저장된 개수와 서버가 실제로 받은 개수로 나눠 비교해봤습니다.

| 측정 범위       | 브라우저 저장 |  서버 수신 |   차이 |
| ----------- | ------: | -----: | ---: |
| 한 녹음 세션     |  3,211개 | 2,695개 | 516개 |
| 로컬 재현 3회 합계 |  7,159개 | 6,524개 | 635개 |

결과는 생각했던 것 보다 많은 양이 서버에 도착하지 않았습니다. 자세히는 세 번 재현한 세션 중 한 세션에서는 516개, 시간으로 치면 약 10.3초 분량의 오디오가 서버에 도착하지 않았습니다. 세 번을 모두 합치면 브라우저에 저장된 청크의 **8.9%가 서버 수신 기록에 없었습니다.**

브라우저 쪽에서 보면 전송은 문제없이 끝난 것처럼 보였습니다. 소켓이 닫혀서 `send()`조차 못 한 청크는 하나도 없었고, 연결이 끝날 때 `bufferedAmount`도 0바이트였습니다. 그런데도 데이터가 빠진 이유는, 이 값들이 각각 의미하는 범위가 달랐기 때문입니다.

- `send()` 반환: 브라우저가 전송 요청을 송신 큐에 넣음
- `bufferedAmount` 0: 브라우저가 집계하는 송신 큐에 아직 네트워크로 넘기지 않은 바이트가 없음
- 서버 수신: 서버가 처리한 순번을 알려줘야만 확인 가능

앞의 두 값은 브라우저에서 확인할 수 있는 정보일 뿐, 데이터가 서버까지 도착해 처리됐는지는 알려주지 않습니다. 결국 서버 수신 여부는 서버가 직접 알려주지 않는 한 확인할 수 없었습니다.

그래서 서버가 마지막으로 처리한 청크 순번을 브라우저에 알려주고, 브라우저는 그 순번 이후의 확인되지 않은 청크만 다시 보내도록 구조를 바꿨습니다.

## 왜 저장소까지 바꿔야 했을까요?

재전송하려면 “녹음 파일 전체”가 아니라 **서버가 받았다고 확인하지 않은 특정 청크**를 찾아야 합니다. 기존 OPFS 구조는 `MediaRecorder` 객체마다 part 파일을 열고 청크를 순서대로 이어 붙였습니다. 종료 후 파일을 합치는 목적에는 맞았지만, 파일 안에서 청크 경계를 다시 찾거나 각 청크에 수신 확인 상태를 붙이기는 어려웠습니다.

필요한 것은 **청크별 보관**, **수신 상태 기록**, **미확인 청크 조회**였습니다. 다른 저장소도 이 기준으로 살펴봤습니다.

- **OPFS에 청크별 파일 생성:** 가능하지만 약 20ms마다 파일이 늘어나고, 미확인 청크를 찾으려면 별도 상태 관리와 디렉터리 순회가 필요합니다.
- **`localStorage`:** 문자열만 저장할 수 있어 녹음 청크 같은 바이너리 데이터를 담기 어렵고, 잦은 쓰기에도 적합하지 않습니다.
- **Cache API:** 바이너리는 보관할 수 있지만 상태별 조회 인덱스가 없습니다.

그래서 IndexedDB를 선택했습니다.

## IndexedDB를 쓰면서 왜 `idb`를 골랐을까요?

브라우저의 IndexedDB API는 `get()`을 호출해도 값 대신 `IDBRequest`를 반환합니다. 결과를 이벤트로 받아야 하고, 요청 성공과 트랜잭션 완료도 따로 확인해야 합니다. 복합 키·상태 인덱스·Blob 저장을 사용하면서 이 비동기 처리를 단순하게 만드는 라이브러리가 필요했습니다.

| 라이브러리 | 이번 작업에서의 판단 |
| --- | --- |
| `idb-keyval` | 키·값 저장은 간단하지만 `pending` 상태 인덱스 조회에 맞지 않았습니다. |
| Dexie | 쿼리 기능이 풍부하지만 이번 저장·조회·상태 변경에는 그만큼의 추상화가 필요하지 않았습니다. |
| **`idb`** | IndexedDB의 저장소·인덱스를 그대로 쓰면서 Promise와 TypeScript 타입으로 다룰 수 있습니다. |

라이브러리를 고를 때는 기능의 수보다 **필요한 조회를 명확히 표현할 수 있는지**를 봤습니다.

## 청크와 수신 상태를 어떻게 기록했을까요?

각 청크를 `[recordingSessionId, seq]`로 식별하고, `[recordingSessionId, status]` 인덱스로 해당 회의에서 아직 확인되지 않은 청크만 찾도록 했습니다.

`seq`는 청크의 순번이자 재전송 순서이고, `status`는 **전송 시도 여부가 아니라 서버 수신 확인 여부**입니다. 앞선 실험에서는 `send()`를 호출한 청크도 서버에 도착하지 않았기 때문입니다.

저장 방식을 바꾸더라도 회의가 끝난 뒤 녹음 파일은 계속 만들어야 했습니다. 일시정지나 재연결 뒤에는 새 `MediaRecorder` 객체가 생겨 독립된 WebM 조각이 만들어집니다. 그래서 청크에 `partIndex`도 함께 저장했습니다. 재전송은 `seq` 단위로 하고, 회의 종료 후 파일을 만들 때는 같은 `partIndex`의 청크를 모아 병합합니다. 서버가 받은 청크도 최종 녹음 파일에는 필요하므로 확인 직후 삭제하지 않습니다.

## 저장한 청크를 언제 다시 보낼까요?

저장소를 바꾼 뒤에는 브라우저가 청크마다 순번을 부여했습니다. 그 순번을 오디오와 함께 서버로 보내고, IndexedDB의 키에도 사용했습니다. 처음 저장한 청크는 `pending`입니다. 이후 서버가 누적 ACK로 처리한 순번을 알려주면, 그 순번까지를 `acked`로 바꿉니다. ACK가 청크 저장보다 먼저 도착할 수 있으므로, 상태 변경은 청크 저장 작업이 끝난 뒤 처리했습니다.

인터넷 연결이 끊겼다가 돌아오면 서버가 마지막으로 처리한 순번을 알려줍니다. 브라우저는 그 순번까지 `acked`로 바꾸고, 남은 `pending` 청크만 순번대로 다시 보냅니다.

## 다시 측정한 결과

개선 후에도 같은 방식으로 로컬에서 연결을 끊어 재현해봤습니다. 이번에도 연결이 끊긴 동안 서버에 닿지 못한 청크는 생겼지만, 연결이 돌아온 뒤 서버가 알려준 순번을 기준으로 351개 청크가 다시 전송됐습니다. 그 결과 브라우저에 저장된 청크와 서버가 최종적으로 받은 청크 수가 정확히 일치했습니다.

| 로컬 측정        | 브라우저 저장 | 서버 최종 수신 |          차이 |
| ------------ | ------: | -------: | ----------: |
| 개선 전 · 3개 세션 |  7,159개 |   6,524개 | 635개 (8.9%) |
| 개선 후 · 재측정   |  3,537개 |   3,537개 |     0개 (0%) |

다만 두 수치는 서로 다른 재현 세션에서 얻은 결과라, 이것만으로 어떤 네트워크 상황에서도 유실이 없다고 말하기는 어렵습니다. 그래도 적어도 재현했던 끊김 상황에서는, 서버가 받지 못한 청크를 브라우저가 찾아 다시 보내는 흐름이 의도대로 동작한다는 것을 확인할 수 있었습니다.

이제 연결이 잠시 끊기더라도 확인되지 않은 녹음 데이터는 다시 전송되기 때문에, 실시간 전사에서 발언이 빠지거나 녹음 파일과 전사의 시점이 어긋날 위험을 줄일 수 있었습니다.

이번 작업에서 가장 크게 배운 점은, 브라우저가 보냈다는 것과 서버가 받았다는 것은 다르다는 사실이었습니다. 처음에는 send()가 정상적으로 반환되고 bufferedAmount가 0이면 전송이 끝났다고 생각했지만, 이 값들은 브라우저 안에서의 상태만 알려줄 뿐이었습니다. 데이터가 정말 도착했는지는 결국 받는 쪽이 확인해줘야 알 수 있었습니다.

실시간 전사처럼 데이터가 끊김 없이 이어져야 하는 기능에서는, 이런 작은 차이가 사용자가 체감하는 "빠진 발언"으로 이어집니다. 그래서 전송 여부를 브라우저의 추측이 아니라 서버의 확인을 기준으로 판단하도록 바꿨고, 덕분에 Meety는 네트워크 상황에 흔들리지 않고 회의를 끝까지 기록하는 서비스에 한 걸음 더 가까워졌습니다.
