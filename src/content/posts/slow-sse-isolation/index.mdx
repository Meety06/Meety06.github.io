안녕하세요, Meety BE 개발자 Jay입니다.

Meety는 회의 중 생성된 전사와 녹음 상태 변경을 SSE로 전달합니다. 여러 BE 서버에서 발생한 이벤트를 공유하기 위해 Redis Pub/Sub을 사용하고 있습니다.

문제는 한 회의의 SSE 전송이 느려지면 해당 회의뿐 아니라 다른 회의의 이벤트 처리까지 지연될 수 있다는 점이었습니다. 실제 Redis 환경에서 특정 SSE 전송에 500ms 지연을 주자, 다른 회의의 이벤트와 알림 처리까지 약 500ms가 걸렸습니다.

이 글에서는 원인을 어떻게 확인했고, 왜 단순한 비동기화 대신 회의별 큐를 도입했는지 정리합니다.

## Redis Pub/Sub을 이용한 회의 이벤트 전달 구조

SSE 연결은 그 연결을 받은 BE 서버의 메모리에 있습니다. 이벤트가 발생한 서버와 사용자가 연결된 서버가 다를 수 있으므로, 이벤트를 Redis로 발행하고 각 서버가 구독해 자신이 가진 연결로 전송합니다.

## 다른 회의가 영향을 받는 이유를 의심하다

회의마다 SSE 연결을 별도로 관리하므로 서로 영향을 주지 않을 것이라고 생각하기 쉽습니다. 하지만 연결이 분리되어 있다고 실행 스레드까지 분리된 것은 아닙니다. 그래서 Redis 메시지를 수신한 이후 어떤 스레드에서 SSE 전송이 실행되는지부터 살펴봤습니다.

## 기존 Redis Listener 실행 구조 확인

`RedisMessageListenerContainer`는 `SyncTaskExecutor`를 사용하고 있었고, 구독부터 전송까지 같은 실행 흐름에서 처리됐습니다.

```text
Redis 메시지 수신
→ MeetingSseSubscriber
→ MeetingSseRegistry
→ SseEmitter.send()   (네트워크 전송이 끝날 때까지 대기)
```

즉, 메시지를 받은 흐름이 네트워크 전송까지 동기적으로 실행합니다. 한 번의 전송이 느려지면 뒤에 있는 메시지도 함께 기다립니다. 같은 Container를 쓰는 알림 처리도 마찬가지입니다.

## 500ms 느린 SSE 연결로 문제 재현

Slow Emitter의 `send()`를 약 500ms 지연시키고 실제 Redis 통합 테스트로 측정했습니다. 느린 회의 A를 처리하는 동안 회의 B와 알림 처리 모두 약 508ms가 걸렸습니다. Redis가 느린 것이 아니라, 느린 네트워크 전송이 수신 흐름을 붙잡고 있다는 사실을 확인했습니다.

## 단순 비동기화만으로 충분하지 않았던 이유

전송을 공용 스레드 풀로 넘기기만 하면 수신 흐름은 빨리 끝납니다. 하지만 두 가지 문제가 남습니다.

- **순서:** 같은 회의의 이벤트가 여러 스레드에 나뉘면 순서가 보장되지 않습니다. 브로드캐스트보다 연결 종료가 먼저 실행될 수도 있습니다.
- **대기량:** 제한이 없는 대기열은 느린 연결이 있을 때 메모리에 계속 쌓입니다.

## 회의별 FIFO 큐와 전용 Executor 도입

`MeetingSseDispatcher`를 추가해 `meetingId`별로 큐를 관리했습니다. 같은 회의의 명령은 FIFO로 처리하고, 서로 다른 회의는 전용 Executor의 다른 Worker에서 병렬로 처리합니다.

```text
Redis Listener → 회의별 Queue → Meeting SSE 전용 Executor → SseEmitter.send()
```

순서를 보장하는 명령은 `BROADCAST`, `COMPLETE_PARTICIPANT`, `COMPLETE_ALL`, `SEND_AND_COMPLETE_ALL`입니다. 큐가 비면 정리하며, 등록과 정리가 경쟁하는 상황도 테스트로 검증했습니다. 전송에 실패하면 기존처럼 해당 emitter만 제거합니다.

## 큐 용량 제한과 이벤트 거절 정책

```text
Executor: core=4 / max=4 / queue=100, AbortPolicy
회의별 pending 최대 100
서버 전체 pending 최대 1,000
포화 시 이벤트 거절, WARN 로그와 Counter 기록
```

포화 시 Redis Listener가 직접 전송하는 fallback은 일부러 넣지 않았습니다. 그렇게 하면 부하가 가장 높은 순간에 처음의 병목이 그대로 돌아오기 때문입니다.

## 개선 전후 지연 비교

```text
측정 항목                      개선 전       개선 후
Subscriber 진입 → 반환        508.422ms     0.902ms
A 처리 중 Meeting B 처리      508.022ms     1.361ms
A 처리 중 Notification 처리   508.321ms     2.212ms
Meeting A 자체 send()         507.579ms     503.584ms
```

마지막 줄이 중요합니다. 느린 전송 자체는 여전히 약 500ms입니다. 이번 개선은 전송을 빠르게 만든 것이 아니라, 그 지연이 Redis Listener와 다른 회의로 전파되지 않도록 실행 경계를 나눈 것입니다.

## 여전히 남은 문제: 느린 연결과 이벤트 유실 가능성

- **이벤트 거절:** 큐가 가득 차면 이벤트는 거절됩니다. 지연을 막는 대신 유실을 선택한 정책입니다.
- **메모리 큐:** 큐가 메모리에 있으므로 서버가 종료되면 대기 중인 이벤트도 함께 사라질 수 있습니다.
- **Worker 점유:** Worker가 4개이므로 느린 회의가 많아지면 Worker를 함께 점유해 다른 회의도 대기할 수 있습니다.

이 측정은 Slow Emitter를 이용한 통합 테스트 결과이며, 실제 사용자 네트워크 조건에서 측정한 값은 아닙니다.

이번 작업에서 얻은 교훈은 간단합니다. 연결을 분리하는 것과 실행 흐름을 분리하는 것은 다른 문제입니다.
