안녕하세요. Meety 서비스의 FE 개발자 chloe입니다.

녹음 중 AAC를 만들도록 바꾸면서 회의 종료 시 파일 준비 시간은 크게 줄었습니다. 스테이징 5분 녹음에서는 6,591ms에서 289ms로 감소했습니다. 하지만 **파일 준비가 끝나는 것과 사용자가 회의를 끝낼 수 있는 것은 달랐습니다.** 업로드가 느리거나 실패하면 종료 흐름도 함께 멈췄기 때문입니다.

이 글은 현재 열려 있는 [회의 종료와 녹음 파일 업로드 분리 이슈 #372](https://github.com/100-hours-a-week/KTB4-6th-FE/issues/372)를 바탕으로 한 **설계안**입니다. 아래의 분리 흐름과 Worker 도입은 완료된 개선 결과가 아닙니다. 무엇을 바꿔야 하는지, 어떤 순서로 검증할지를 정리합니다.

## 지금은 업로드가 종료 버튼 앞에 서 있습니다

현재 종료 흐름은 대체로 다음 순서로 이어집니다.

~~~text
PCM 마지막 조각 저장
  → 인코딩 마무리
  → MP4 구성
  → S3 업로드
  → 업로드 완료 API
  → 녹음 종료 API
  → 화면 전환
~~~

파일 준비는 빨라졌어도 업로드는 네트워크 속도의 영향을 받습니다. Slow 4G를 흉내 낸 로컬 측정에서 90분 분량의 녹음 파일 업로드는 6.7분 걸렸습니다. 이 수치는 실제 S3가 아니라 가짜 S3를 사용한 부하 측정이며, 보통 회의의 종료 시간을 뜻하지는 않습니다. 그러나 업로드가 끝날 때까지 종료 API를 호출하지 않는 구조의 약점을 분명히 보여줍니다. 업로드에 실패하면 회의가 계속 진행 중으로 남을 수도 있습니다. [측정 환경과 남은 문제는 #309에 기록했습니다.](https://github.com/100-hours-a-week/KTB4-6th-FE/issues/309#issuecomment-6336414559)

## 먼저 종료의 완료 조건을 바꾸려고 합니다

제안하는 첫 단계는 **PCM 마지막 조각이 IndexedDB에 저장된 것을 확인한 뒤, 녹음 종료 API를 호출하고 화면을 전환하는 것**입니다. 인코딩 마무리, MP4 구성, 업로드는 앱 전역의 업로더가 이어서 처리합니다. 이렇게 하면 사용자가 기다리는 종료 동작과 네트워크 전송을 분리할 수 있습니다.

다만 FE 흐름만 바꾸고 끝낼 수는 없습니다. 백엔드가 <code>COMPLETED</code> 상태의 녹음 세션에도 업로드 URL 발급과 업로드 완료 처리를 허용하는지, 종료 직후 녹음 파일이 필요한 후처리가 없는지 확인해야 합니다. 파일이 아직 준비되지 않은 종료 화면의 표시 방식도 정해야 합니다. 이 선행 조건이 확인되기 전에는 “종료 API를 먼저 호출하면 된다”고 단정할 수 없습니다.

## 탭을 닫아도 남아야 할 것은 업로드 상태입니다

앱 전역 업로더로 옮기는 것만으로는 새로고침과 탭 종료에 대비할 수 없습니다. 현재 메모리에만 있는 업로드 대기 상태는 페이지가 사라지면 함께 없어집니다. 제안안에서는 업로드 대기 세션을 IndexedDB에 기록하고, 다시 접속했을 때 남은 작업을 찾아 재시도합니다.

사용자가 탭을 닫는 동안에도 브라우저가 계속 업로드한다는 뜻은 아닙니다. 작업이 중단되면 **다음 접속 때 다시 시작할 근거를 남긴다**는 뜻입니다. 업로드 성공 전에는 PCM과 AAC 프레임을 지우지 않고, 성공 후에만 정리해야 재시도할 데이터가 남습니다. 업로드 중 이탈에는 경고를 표시하고, 기존의 다른 종료 경로도 같은 업로더를 사용하도록 맞춰야 합니다.

## Worker는 측정 후에 결정합니다

회의 종료와 업로드를 분리해도, 긴 녹음의 인코딩 마무리나 MP4 구성 작업이 메인 스레드에서 화면 조작을 느리게 만들 수 있습니다. Dedicated Worker는 이 계산을 메인 스레드 밖으로 옮길 후보입니다. 그러나 **Worker가 네트워크 업로드 시간을 줄여주지는 않습니다.** 업로드 완료를 기다리지 않게 만드는 핵심은 종료와 업로드의 순서를 분리하는 데 있습니다.

따라서 순서를 두 단계로 나눴습니다.

1. 먼저 메인 스레드에서 종료와 업로드를 분리하고, 장시간 녹음의 MP4 구성 중 Long Task와 메모리 사용량을 측정합니다.
2. 화면 조작에 실제 영향이 확인되면 인코딩 마무리와 MP4 구성만 Dedicated Worker로 옮기고 전후를 비교합니다. 인증이 필요한 API 호출은 메인 스레드에 남깁니다.

Dedicated Worker는 탭이 닫히면 함께 종료됩니다. 그러므로 Worker는 **화면 응답성**을 위한 선택이고, 접속을 다시 했을 때의 **작업 복구**는 IndexedDB에 기록한 업로드 대기 상태가 맡습니다.

## 성공했다고 말하려면

이 설계의 완료 기준은 “종료 버튼이 빨라 보인다”가 아닙니다. 업로드 중이거나 실패해도 회의 종료가 완료되는지, 새로고침 후 남은 업로드가 재시도되는지, 업로드 성공 전 원본 데이터가 보존되는지 확인해야 합니다. Worker를 도입한다면 Long Task가 실제로 줄었는지도 별도로 측정해야 합니다.

앞선 세 편은 잃어버린 청크를 찾아 다시 보내고, 다시 보낸 음성을 읽을 수 있게 하고, 녹음 파일을 이어 만드는 과정이었습니다. 마지막 과제는 **그 파일을 올리는 일이 사용자에게 회의 종료를 기다리게 하지 않도록 만드는 것**입니다. 이 글은 그 변경의 출발점이며, 구현과 측정 결과는 완료 뒤에 업데이트하겠습니다.
